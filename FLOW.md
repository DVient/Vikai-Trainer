## PHASE 7: BODY-MAP SORENESS & TARGETED ADJUSTMENT
*Goal: close the expert-review gap — the app adjusts for WHAT is sore, not just how much. Today's workout derives from everything logged since the last workout (post-session feedback, completed work) plus this morning's check-in; once derived it never mutates mid-session.*

* [x] **7.1 Domain types & body-map catalog** (`src/types/index.ts`, `src/lib/bodyMap.ts`):
  * `SoreArea` / `SoreRegion` unions, canonical `SORE_AREA_IDS`, `isSoreArea` guard.
  * Region→area display catalog with labels/emoji; `ReadinessInput.soreAreas?`, `TrainingRestrictions.sorenessScale?`, `TrainingComponent.muscleGroups?` (all additive).
* [x] **7.2 Engine targeted scales** (`src/engine/autoregulation.ts`):
  * `soreAreas` → per-area `sorenessScale` (configurable `soreAreaScale`, default 0.6), merged min across fired rules; `SORENESS_FLAGGED` reason, YELLOW-only.
  * §16 `PAIN_CONCERN` path untouched: still RED + adult attention, still takes precedence over soreness.
* [x] **7.3 Stepped check-in body map** (`app/checkin.tsx`):
  * Optional section after Energy: region cards (default = 💪 all good, zero friction) → area chips only for flagged regions; hidden on the pain path; collapsing a region clears its flags; saved only when non-empty.
* [x] **7.4 Library muscle tags** (`src/plans/library.ts`, `src/plans/basePlan.ts`):
  * Every PHYSICAL block declares `muscleGroups`; SKILL and RECOVERY blocks stay untagged (never sore-scaled); `DEFAULT_BASE_PLAN` mirrors the library tags (consistency-tested).
* [x] **7.5 Generator targeted mapping** (`src/engine/generator.ts`):
  * Block whose every targeted area is sore sits out (reason names the areas); partial overlap scales by `regionScale × sorest overlap` with sore-aware copy; untagged blocks exempt; §23 stripping order preserved.

## PHASE 8: FEEDBACK LOOP & PERFORMANCE LOADING
*Goal: the athlete's model — today's workout is adjusted by the inputs given after the last workout (post-session body map, completed-work performance) and before today's workout (morning check-in); once derived it never mutates mid-session.*

* [x] **8.1 Post-session soreness capture** (`app/workout.tsx`, `src/components/BodyMap.tsx`, `src/types/index.ts`):
  * Two-step Finish: the CTA reveals the shared body-map card ("This prices tomorrow's workout — today's plan is already locked"); flagged areas persist as `WorkoutLog.soreAreasAfter`; a skip path closes without notes. Daily check-in refactored onto the same shared `BodyMap` component.
* [x] **8.2 Next-day derivation** (`src/lib/engine-bridge.ts`, `src/hooks/useEngineResult.ts`):
  * The bridge composes today's effective sore areas from the morning check-in ∪ the latest workout log BEFORE today (deduplicated, unknown ids dropped); today's own log never feeds back. SORENESS_FLAGGED surfaces on Home's Game Plan card and the session screen ("Sore today: … — blocks targeting them are scaled").
* [x] **8.3 Performance-based loading** (`src/plans/adherence.ts`, generator option):
  * Objective per-goal completion ratios over the last 7 days of sessions (planned vs checked-off blocks, recovery excluded); under-completed eligible goals (ratio < 0.75 over ≥ 3 blocks) auto-scale the next session at 0.8. Exempt by design: EXPLOSIVENESS (skills/power), SPEED, RECOVERY. Engine never sees adherence data — the generator consumes it as a mapping option.
* [x] **8.4 Spec audit extension** (`tests/spec-audit.test.ts`):
  * New automated assertions: `src/engine/` imports no framework/storage/clock dependencies and constructs no ambient clocks; body-map and generator copy stay non-medical.

* [x] **9.2 Weekday-structured default plan** (`src/plans/basePlan.ts`):

* [x] **9.4 Calendar planned workouts** (`src/lib/calendar.ts`, `app/history.tsx`, `CalendarGrid`):

  ** Choosing a day on the grid shows **that day's contents inside the Scheduled card** (planned row + full timeline), with a "Next 7 days" chip to return to the week view. Pure `weekSchedule()` helper replaces `upcomingEventRows`.
* [x] **9.7 Body-map impact audit & feedback-loop hole fix** (`src/engine/autoregulation.ts`, `src/lib/engine-bridge.ts`, `src/types/index.ts` — user review):
  * **Audit verdict:** the loop is wired end-to-end — morning body map and last session's close → deduped engine input → `SORENESS_FLAGGED` (0.6× per area) → generator block mapping (QUAD-only blocks sit out; partial-overlap blocks run at the sorest area's scale; skills/recovery exempt) → scaled "sets" targets on screen.
  * **Hole found:** a skipped morning check-in dropped the carried post-session body map entirely (engine returned bare baseline on `CHECKIN_REQUIRED`).
  * **Fix:** `EngineInput` gains top-level `carriedSoreAreas`; the engine unions it with the check-in's own map on every path — the `CHECKIN_REQUIRED` restrictions now price carried soreness while status semantics stay untouched (§27). New end-to-end integration tests pin input → engine → prescription for both inputs.
* [x] **9.8 Soreness is status-neutral** (`src/engine/autoregulation.ts` — user review "one sore arm shouldn't tank the battery"):
  * **Audit:** the battery number never came from the body map (it reads region scales — a borderline-readiness arithmetic day is what showed 60%); but the soreness rule DID flip the day YELLOW, recoloring everything for one flagged area — contradicting the block-targeted design and rendering an incoherent "Power Save 100%".
  * **Fix:** the global status now derives from global rules only — `SORENESS_FLAGGED` contributes its restrictions (scaled blocks, stripped optional accessories, amber sore line) but never the status. Soreness-only day: GREEN battery "Full Send", GO game plan, arm blocks dialed down with named reasons. Combined days take status from the global rule. The borderline readiness rule's recovery action now states its score ("6/9") so the battery explains itself.
* [x] **9.9 Protocol audit (Charlie Francis high/low × Fred Duncan basketball S&C) + week-structure corrections** (`src/plans/weekStructure.ts` new, `basePlan.ts`, `planBuilder.ts`, `fall2026.ts`, `config/defaults.ts` — user review):
  * **Verdict:** adaptive rails already protocol-grade (daily low-fatigue skill work, Francis-format speed sessions with full rests, tempo runs, game windows, §20/§26, deload/taper progression, soreness pricing). Deviations: speed trained after lifting; practice-season Friday ran the full speed stack ~18h after the third practice; the pre-season overlay's designed high/low week never rendered; `firstGame` was a Thursday against "games on Saturdays" copy.
  * **Fix — one shared week skeleton** (`dayRoleFor`/`componentsForRole`/`sessionOrder`): Sunday recovery; practice nights (Tue/Wed/Thu ≥ seasonStart) save the legs; practice-season Friday is post-practice (no speed/plyo/COD); pre-season Mon/Wed/Fri are low days with Tue/Thu/Sat high. **Built plans now shape by the same weekday roles** (`activePlanForDay`), not just the default — a customized plan inherits the high/low skeleton. Speed-power blocks render first in every session. Default base plan reordered speed-first; overlay completions (pre-season low-day speed/COD empties, competition game-day jumps empty); `firstGame` → 2026-10-17.
* [x] **9.10 Offline exercise guidance: technique steps everywhere + curated online-only demos** (`fall2026.ts`, `library.ts`, `ExerciseDetailList.tsx`, `workout.tsx` — user decisions: steps now / visuals later, curated videos kept as online-only):
  * **Problem:** every link in the plan was a YouTube *search-results* page (none was a specific video) — no real demonstrations, and they break offline, the app's core promise.
  * **Fix — two layers:** (1) `steps` on every exercise in BOTH libraries (`FALL_COMPONENT_DETAILS` and `BLOCK_LIBRARY`, ~85 exercise lines): 3 numbered technique points (setup → execution → key point) — the guaranteed offline layer, zero network needed. (2) `videoUrl` is now an optional curated SPECIFIC video (`youtube.com/watch?v=…`) marked "Needs internet" in the UI; `videoSearchUrl()` and all `videoQuery` fallbacks are deleted. Guardrail tests enforce both: steps ≥2 lines on every exercise, and no `results?search_query` link may ever return.
  * **Note:** the curated video IDs are a draft — the trainer opens each link once and verifies the content before release (one-string swap in the `DEMO` maps). Later-phase hook: pattern-level bundled demo clips (filmed or Lottie) slot in under the same structure.
* [x] **9.11 Distribution for the 3–4 users: Android APK now, Apple later** (`INSTALL.md` new, `eas.json`/`app.json` already build-ready — user decision: Android-only for now):
  * **Model:** no app store at this scale. Android users install from a private EAS APK link (`eas build -p android --profile preview` → permanent URL → "allow from this source" → install). All app-logic updates ship over the air via `eas update` — nobody reinstalls. `eas init` + `eas update:configure` wire the project id and updates URL.
  * **Prepped for later:** Apple requires the Developer Program ($99/yr) before any iPhone install; `eas.json` production profile + `submit` and the iOS bundle id are already in place, and `INSTALL.md` documents the exact future TestFlight switch-on (enroll → build+submit → invite testers by email → 3-tap install; builds expire after 90 days).
* [x] **9.12 Missed-day backfill + data export + hands-free OTA** (`store`, `practice-log.tsx`, `history.tsx`, `index.tsx`, `src/lib/export.ts` new, `.github/workflows/ota-update.yml` new, `INSTALL.md` — user requests):
  * **Backfill:** forgetting to log a day no longer locks the record. The store gains `updateWorkoutLog(id, patch)`; the Practice Log screen doubles as a past-day editor via `?date=YYYY-MM-DD` — dated header, entries saved onto that date, a post-session body-map card for that day's session record, and check-offs for the day's blocks (recovery-role plan on low days). The calendar's past-day card gains **"＋ Update this day — it shapes today's plan"**, and Home shows a per-date dismissible "Did anything happen yesterday?" nudge when yesterday is empty. All backfilled inputs land in the same slices the engine already reads, so today's Game Plan prices them immediately; past *morning* check-ins stay record-only by design (the engine reads today's only).
  * **Export:** pure `buildExport(state, now)` produces a canonical restore-grade JSON (`vikai-export/1`, every slice) and a sectioned RFC-4180 CSV (Check-ins / Activities / Sessions / Blocks done / Events / Benchmarks; pipe-joined lists, ISO dates, load = effort × minutes). The calendar screen gains a "Your data" card — JSON backup or Spreadsheet via the OS share sheet (`expo-file-system` cache file + `expo-sharing`), file name carries the export date. No server involved (AGENTS.md).
  * **OTA pipeline:** pushing to GitHub `main` runs `.github/workflows/ota-update.yml` — pnpm install, `tsc`, full Vitest gate, then `eas update --channel preview` with the commit subject as the message. APK users on the preview channel receive JS changes at next launch; native changes still need a manual `eas build`. `EXPO_TOKEN` secret is the one-time setup; INSTALL.md documents both the flow and the exception.
  * **Post-release crash fix (learned the hard way):** the export screen originally imported `expo-file-system`/`expo-sharing` at module scope, so the first OTA crashed the calendar on every APK built before those packages existed — OTA adds JavaScript but never native code. The imports are now dynamic and guarded (tests/export-crash-guard.test.tsx pins it with throwing module factories): old APKs render the screen and the export button degrades to a friendly note; APKs built with the modules get the full share-sheet feature. Rule for the future: any new native-backed package ships only with the next `eas build`, never as a module-scope import in an OTA.
* [x] **9.13 Device bug triage: dead save button, ghost toast overlay, unresponsive taps, calendar overlap** (`event-form.tsx`, `checkin.tsx`, `practice-log.tsx`, `Toast.tsx`, `history.tsx` — device feedback):
  * **Ghost toast = the white circle on Save.** Event-form held its toast in `useState("")` while Toast hides on `null` only — an empty white pill rendered from mount, absolutely positioned over the bottom of the form, exactly on the Save button, swallowing its touches (a plain overlay View blocks presses in RN). State is now `useState<string | null>(null)` (matching check-in/practice-log) and the Toast guard itself is hardened to hide on any falsy message, so this failure class can't return. Regression tests: Toast renders nothing for `""`/`null`, everything for a real message; the event form shows no toast until a successful save.
  * **Intermittent unresponsiveness = keyboard handling.** All three input screens used `KeyboardAvoidingView behavior="height"` on Android, where the OS already resizes the window (Expo default `softwareKeyboardLayoutMode: resize`) — the double compensation leaves hitboxes desynced after the keyboard closes. Behavior is now iOS-only `padding`, and the form ScrollViews gained `keyboardShouldPersistTaps="handled"` so a button answers on the first tap even with the keyboard open (previously the first tap only dismissed the keyboard).
  * **Calendar overlap.** The long uppercase labels in the two `flex-row justify-between` headers ("Add your commitments — they shape the plan" beside ＋ Add, "Scheduled — tap to change time or day" beside Next 7 days) had no `flex-1`; RN defaults `flexShrink` to 0, so the label rendered at full single-line width and overflowed underneath the button. Labels are now `flex-1` and wrap cleanly; the "Scheduled — tap to change time or day" label sits beside the "Next 7 days" button the same way. 438 tests.
